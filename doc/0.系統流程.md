# 0. 系統流程｜AICAR 開發階段與跨主機驗證矩陣

> 文件定位：本篇為 AICAR 專案 `doc/` 的導讀文件，先區分三種測試環境，再依八階段安排工作，最後判斷何時需要本機 WSL2 與 Raspberry Pi 互通。
> 基準日期：2026-11-21。本文為專案開發／驗證規劃，不表示所有階段已驗收完成。具體操作與本輪結果請參照 [01](01-os-hosts.md)～[08](08-aicar-hardware-urdf-physical-model.md)。

## 一、三種驗證環境

三種環境相互補充，不要求先做完 A 才能做 B。

### A｜純軟體開發／模擬（本機單機）

```text
本機電腦（Windows 11 → WSL2 Ubuntu 24.04）
  ├── ROS2 Jazzy：Nodes、Topics、TF、SLAM（依實驗啟動）
  ├── Gazebo Harmonic：物理、感測器、機器人模擬
  └── RViz2：機器人狀態、TF、地圖、感測器資料視覺化
```

使用模擬資料，**不需要 Raspberry Pi 或實車連線**。但是另一台新電腦仍須配置相容環境、模型與依賴。Gazebo 與 ROS2 間傳輸模擬資料，通常需配置對應 Bridge。RViz2 能啟動並不等於已成功顯示 RobotModel。

### B｜實體車單機驗證（車端單機）

```text
Raspberry Pi（Ubuntu 24.04 ARM64）
  ├── ROS2 車端節點（Base / IMU / Odom；依部署配置）
  └── DYNAMIXEL / IMU / LiDAR（實際有安裝、驅動可用的設備）
```

程式與硬體直接連接，**完成部署後可以不依賴本機電腦持續連線**。前提是車端具備所需運算資源、軟體與必要的獨立時間來源／安全控制。馬達啟動前必須做安全停止、速度／力矩限制等驗證。

### C｜跨主機整合驗證（兩端互通）

```text
本機 WSL2                              Raspberry Pi
RViz2 / SLAM / Teleop  ← ROS2/Zenoh →  感測器 / 馬達 / Odometry
192.168.123.2                          192.168.123.1
       └──────── Ethernet / Wi-Fi ────────────┘
             Topic、TF、時間戳、失聯安全測試
```

這是**分散式部署**：當本機需要即時接收車端資料、下發控制或運行位於本機的 SLAM 時，兩端必須連通，並檢查資料品質、時間同步和控制安全。目前已驗證雙向測試 Topic 與基本校時，但不能因此推定完整的 SLAM／控制鏈通過。

## 二、從零開始開發機器人的八階段流程

以下以 AICAR「四輪移動底盤＋小型機械手臂＋感測器＋ROS2」為例。這是工程化規劃，不是所有產業公司的唯一標準；開發過程可反覆迭代。

| 階段 | 主要工作與驗收 | 需要本機與車連通？ |
|---|---|---|
| **01 需求與系統架構** | 功能、速度、載重、續航、安全、運算分工；定義驗收條件 | 不需要 |
| **02 機械與電氣設計** | CAD、馬達選型、輪距、質心、電源、配線；實測尺寸／質量核對 | 不需要；實測需要硬體 |
| **03 軟體與通訊架構** | ROS2 Nodes、Topics、TF、QoS、部署拓樸、介面契約 | 不需要 |
| **04 模擬與數位模型** | URDF、Gazebo、RViz2、感測器與物理模擬；功能／模型檢查 | 不需要 |
| **05 硬體 Bring-up** | Pi、馬達、IMU、LiDAR、驅動器、安全停止；單元測試 | 不一定；可在 Pi 單機 |
| **06 跨主機整合** | 網路、Zenoh、時間同步、端到端訊息、失聯測試 | **需要**（此階段本身即測試兩端） |
| **07 自主功能驗證** | Odometry、SLAM、導航、避障、手臂控制；模擬／回放／實機 | 依部署方式而定 |
| **08 系統驗收與部署** | 場景測試、故障恢復、版本固定、實機驗證、可重現部署 | 跨主機版本需要；單機版本不一定 |

**迭代範例：** Gazebo 中控制器振盪或車體漂移 → 檢查關節／接觸／控制參數 → 修正並重測；實車若觀測輪胎打滑 → 校準運動模型與 Odometry，再更新模擬。

## 三、目前階段的「兩端校驗」矩陣

| 驗證項目 | 本機 WSL2 | Raspberry Pi | 需要兩端連通？ |
|---|---|---|---|
| ROS2 / Python 版本 | 確認 | 確認 | 不必，同時記錄即可 |
| 原始碼版本 | Commit Hash | Commit Hash | 不必即時連線，但需核對 |
| SSH 連線 | Client | Server | **必須**（測試 SSH 時） |
| Zenoh 通訊 | Router / Node | Client / Node | **必須**（測試跨主機時） |
| ROS2 Topic 跨主機傳輸 | Publish / Subscribe | Subscribe / Publish | **必須** |
| 時間同步 | 時間參考端 | 時間客戶端 | **在目前架構下必須** |
| TF / JointState 時間戳 | 接收與分析 | 發布 | 跨主機使用時必須驗證 |
| IMU / LiDAR 實際數據 | 接收與分析 | 感測器驅動 | 若分析在本機，必須 |
| `/cmd_vel` 到馬達 | 發送命令 | 接收並執行 | 若控制在本機，必須 |
| 失聯安全停止 | 模擬或觸發失聯 | 執行停止機制 | 跨主機部署需做整合測試 |
| Gazebo / RViz2 顯示 | 執行 | 不參與 | 不需要 |

### 必須避免的兩個誤解

**1. 時間同步不是校正一次就永久完成。** 目前 AICAR 採 WSL2 Chrony Server（UDP 1123）→ Pi Chrony Client。跨主機交換帶時間戳的感測資料與 TF 時，除初始校時外，也應在運行期間監測偏差。未來可換成其他可靠的時間來源，不一定永遠由 WSL2 提供 NTP。

**2. 離線安裝不是機器人系統必備的執行流程。** 先前從本機傳遞安裝套件，是因車端當時沒有正常的網際網路連線，屬部署限制。當 Pi 能從可信套件來源正常安裝依賴，這一環節可以不需要本機傳檔。

### SLAM 放在哪個階段？

SLAM 屬於**第 07 階段「自主功能驗證」**，不等於一開始就要上實車：

| 測試模式 | 資料來源 | 兩端要連通？ |
|---|---|---|
| 模擬 SLAM | Gazebo 感測器／里程資料 → ROS2 Bridge → SLAM → RViz2 | 不需要 |
| 離線 SLAM | 已錄製的 rosbag（LiDAR、Odometry、TF 等） | 不需要即時連線 |
| 實機 SLAM：分散部署 | Pi 發布資料；WSL2 運行 SLAM／RViz2 | **需要** |
| 實機 SLAM：車端部署 | Pi 同時運行感測器與 SLAM | 不一定需要 WSL2 持續連線 |

## 四、AICAR 現況與待驗收事項（2026-11-21）

| 事項 | 目前紀錄 | 後續驗證 |
|---|---|---|
| 雙網路 / SSH / Zenoh / Chrony | 本輪已有基本連通與校時測試 | 故障恢復、長時間時鐘偏差與延遲 |
| URDF / Gazebo | 模型載入、重力與關節狀態已測 | 控制器振盪、模型漂移原因 |
| RViz2 | GUI 已啟動 | `Fixed Frame`、TF、RobotModel 尚未驗收 |
| Gazebo → ROS2 Bridge | 尚未驗證 | 隔離模擬 Topic 與實車 Topic |
| SLAM / Nav2 | 未納入本輪完整實車驗收 | 先模擬／資料回放，再整合實車 |
| 跨電腦重建 | 有部署紀錄 | 乾淨環境 Clone、安裝、Build、Smoke Test |

**工程原則：** 「單機能跑」「兩端 Topic 收得到」「系統功能已驗收」是三種不同成熟度，不應互相取代。
